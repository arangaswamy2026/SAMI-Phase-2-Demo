524 raw device alerts — interface flaps, health checks, license notices — generate overwhelming noise. A partner managing 98 tenants cannot triage this manually without missing critical threats buried in routine noise.
SAMI's triage process — 5 steps
1
Ingest & timestamp all alerts
Every alert from all 98 tenants ingested in real-time. SAMI records device ID, tenant, source IP, alert type, and timestamp.
2
Cluster by root cause
ML clustering groups alerts by shared device, IP range, timing pattern, and alert type. 14 interface flap alerts on the same device = 1 group, not 14 rows.
3
Cross-tenant correlation
SAMI compares patterns across tenants. Same C2 beacon on 3 different tenant firewalls = coordinated threat, not 3 independent incidents.
4
Classify: noise vs. action
Each group classified as: Critical (escalate now), Warning (schedule action), Info (noise/auto-resolved). Raw alerts preserved and accessible.
5
Surface with one recommended action
Every group surfaces a single CTA. Escalate to clients. Start renewals. Check switch port. Partner clicks once — SAMI executes.
Grouping rules SAMI applies
Same device, ≤2h window: oscillating up/down alerts → 1 interface flap group
Same IP subnet, multiple tenants: potential cross-tenant threat → escalate immediately
License alerts, same expiry window: batch into a single renewal action
Security alert + correlated system alerts: promote severity to Critical
Known benign pattern (disk scan, report ready): auto-resolve, reduce to info
